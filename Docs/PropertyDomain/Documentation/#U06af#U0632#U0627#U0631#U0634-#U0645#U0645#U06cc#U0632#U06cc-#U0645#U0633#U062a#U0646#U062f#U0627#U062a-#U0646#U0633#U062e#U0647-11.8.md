## ۱. خلاصه مدیریتی

نسخه 11.8 فاقد مستندات نیست؛ برعکس، مجموعه قابل‌توجهی از اسناد پیاده‌سازی، برنامه‌ریزی Sprintها، مهاجرت‌های پایگاه داده، قراردادهای پیام، برنامه‌های آزمون و راهنماهای ماژول‌ها را دارد. مشکل اصلی، **نبود یک نظام مستندسازی یکپارچه و قابل اتکا** است:

1. مستندات در طول Iterationها و Sprintها به‌صورت افزایشی اضافه شده‌اند و هنوز به یک مرجع نهایی و منسجم تبدیل نشده‌اند.
2. سطح جزئیات ماژول‌ها یکسان نیست؛ بعضی READMEها نسبتاً کامل و بعضی فقط معرفی کوتاه دارند.
3. بخشی از اسناد، وضعیت قدیمی قابلیت‌ها را بیان می‌کنند و با کد یا اسناد Iterationهای بعدی هم‌خوان نیستند.
4. فهرست APIها در README ریشه، فهرست کامل و روزآمدی از مسیرهای ثبت‌شده در Endpointها نیست.
5. راهنمای جامع معماری، فرایندهای کسب‌وکار، مدل داده و واژه‌نامه دامنه، راهنمای توسعه‌دهنده، راهنمای استقرار و راهنمای عیب‌یابی به شکل مستقل و منسجم وجود ندارد.
6. توضیحات XML و توضیحات هدفمند در کد کم‌تعدادند؛ مستندسازی رفتارهای عمومی و قراردادهای مهم کد پوشش یکنواخت ندارد.
7. متن بعضی اسناد ترکیبی از فارسی و انگلیسی است. از این مرحله به بعد، **تمام متن توضیحی مستندات باید فارسی باشد**؛ نام کلاس‌ها، جدول‌ها، مسیرها، کدها، شناسه‌ها و اصطلاحات فنی تثبیت‌شده به انگلیسی باقی می‌مانند و در نخستین کاربرد، معادل یا توضیح فارسی می‌گیرند.

### نتیجه ممیزی

وضعیت کلی مستندات: **نیازمند سامان‌دهی و تکمیل ساختاری**؛ نه شروع از صفر.

پیشنهاد می‌شود اسناد موجود حفظ شوند و به‌جای بازنویسی کورکورانه، ابتدا به‌عنوان منابع تاریخی/فنی دسته‌بندی شوند؛ سپس اسناد مرجع فارسی از روی کد نسخه 11.8 و قراردادهای معتبر ساخته شوند. اسناد قدیمی فقط پس از مقایسه با وضعیت جاری، اصلاح یا با برچسب «تاریخی/منسوخ» مشخص شوند.

## ۲. مبنای ممیزی و حدود اطمینان

این ممیزی بر اساس محتوای آرشیو `PropertyDomain.WebApi.Iteration-11.8-Remaining-Sprint-Gap-Closure(1).zip` انجام شده است. موارد زیر بررسی شدند:

- ساختار ریشه پروژه و پوشه‌های `Modules`، `Infrastructure`، `Endpoints`، `Tests` و `Docs`؛
- هفت README ماژول؛
- فهرست Endpointهای Minimal API در فایل‌های Endpoint ماژول‌ها؛
- اسناد معماری/پیاده‌سازی، قراردادهای Integration، Migrationها، Seedها و برنامه‌های آزمون؛
- README ریشه و ارجاع‌های آن به فایل‌های دیگر؛

این مرحله **ممیزی مستندات** است، نه بازبینی کامل صحت منطق کسب‌وکار یا اجرای آزمون‌ها. وجود یک Endpoint یا کلاس در کد، به‌تنهایی اثبات‌کننده صحت رفتاری آن نیست. همچنین Build موفقی که مالک پروژه در محیط خود گزارش کرده، در این ممیزی دوباره اجرا نشده است.

### ۳.۲ وضعیت README ریشه

README ریشه اطلاعات مفیدی درباره فناوری‌ها، Tenant، راه‌اندازی، نمونه درخواست‌ها و تغییرات Iterationها دارد؛ اما در حال حاضر هم‌زمان نقش معرفی محصول، راهنمای نصب، کاتالوگ API، تاریخچه توسعه و گزارش وضعیت را ایفا می‌کند. این اختلاط باعث تکرار و ناسازگاری شده است.

موارد نیازمند اصلاح:

1. در بخش ساخت پایگاه داده، مسیر `Docs/Property Domain-Architecture-Baseline-Integrated.sql` معرفی شده؛ در آرشیو مبنا، فایل موجود `Docs/Database/B-Domain-Architecture-Baseline-Integrated-Optimized.sql` است. مسیر فعلی README با فایل موجود تطبیق ندارد.
2. ادعای نگاشت همه ۶۴ جدول به Entity و DbSet باید با شمارش واقعی مدل EF و اسکریپت Baseline دوباره تطبیق داده شود؛ تا زمان راستی‌آزمایی، این ادعا نباید به‌عنوان واقعیت قطعی در راهنمای اصلی باقی بماند.
3. جدول APIهای README فقط بخشی از مسیرها را فهرست می‌کند؛ فهرست فعلی Endpointهای ماژول‌ها بسیار گسترده‌تر است. بنابراین عنوان «Endpointهای پیاده‌سازی‌شده» ممکن است به‌اشتباه کامل بودن فهرست را القا کند.
4. README در بخش‌های مختلف، قابلیت‌های یک ماژول را در مقاطع زمانی متفاوت توصیف می‌کند. برای مثال، وضعیت‌های قدیمی B04 در کنار توضیحات تکمیل‌شده‌تر Assertion، Assignment، اصلاح تاریخی و Reversal قرار گرفته‌اند.
5. بخش‌های متعدد Iteration و Sprint در README انباشته شده‌اند. تاریخچه باید در گزارش‌های پیاده‌سازی باقی بماند و README فقط وضعیت معتبر نسخه جاری را خلاصه کند.
6. راهنمای راه‌اندازی، Migration نسخه موجود و ساخت پایگاه داده جدید باید از یکدیگر تفکیک شوند؛ این سه سناریو پیش‌نیاز و ترتیب متفاوت دارند.

## ۶. قواعد زبانی و نگارشی اجباری از این مرحله

1. زبان متن توضیحی تمام فایل‌های مستندات: **فارسی**.
2. نام‌های رسمی کد، Namespace، کلاس، متد، Property، جدول، ستون، Schema، Endpoint، Event و کدهای دامنه به همان شکل انگلیسی و بدون ترجمه ساختگی نوشته شوند.
3. اصطلاح انگلیسی تخصصی در نخستین کاربرد با توضیح فارسی معرفی شود؛ برای نمونه: «زمان اعتبار (Valid Time)» و «زمان ثبت (Recorded Time)».
4. عنوان‌ها، شرح‌ها، هشدارها، توضیح جدول‌ها، راهنمای گام‌ها و توضیحات نمودارها فارسی باشند.
5. نمونه درخواست/پاسخ API، قطعه کد، مسیر فایل و نام فنی نباید برای فارسی‌سازی تغییر کنند؛ توضیح پیرامون آن‌ها فارسی باشد.
6. از ترجمه نام‌های رسمی Aggregateها یا کدهای قراردادی به‌گونه‌ای که قابلیت جست‌وجو در کد را از بین ببرد خودداری شود.
7. هر سند باید وضعیت خود را با یکی از برچسب‌های زیر اعلام کند:
   - **معتبر و منطبق با نسخه جاری**
   - **تاریخی — صرفاً برای ردیابی تغییرات**
   - **پیشنهادی — هنوز تصمیم یا تصویب نشده**
   - **نیازمند بازبینی**
8. هر ادعای رفتاری باید به کد، قرارداد، تصمیم مصوب یا آزمون مشخص متصل باشد. حدس و عرف عمومی نباید به‌عنوان قاعده پروژه نوشته شود.

## ۹. مواردی که نباید در مستندسازی حدس زده شوند

- سیاست‌های رسمی و مقادیر مرجع کاتالوگ AuthorizationType و نقش‌های مالک/متصرف/نماینده/وکیل تا زمانی که منبع رسمی ارائه نشده باشد.
- الگوریتم یا سرویس رسمی اعتبارسنجی شناسه ملی اشخاص حقوقی.
- معانی کدهایی که در Check Constraint عددی‌اند اما معنای دامنه‌ای آن‌ها در منبع معتبر تعیین نشده است.
- قواعدی که در Sprintها مجاز دانسته شده‌اند اما انتخاب سیاست نهایی آن‌ها به تصمیم مالک دامنه واگذار شده است.
- وضعیت آزمون‌هایی که صرفاً فایل آزمون یا کد تست دارند ولی اجرا و نتیجه آن‌ها ثبت نشده است.
- قابلیت‌هایی که در گزارش Iteration تاریخی «برنامه‌ریزی‌شده» یا «در حال انجام» بوده‌اند، مگر آنکه وجود پیاده‌سازی جاری در نسخه 11.8 تأیید شود.

برای هر مورد، یکی از سه وضعیت «نیازمند ورودی رسمی»، «نیازمند تصمیم دامنه» یا «نیازمند اجرای آزمون» درج شود؛ هیچ‌یک نباید با توضیح فنی حدسی پر شود.
